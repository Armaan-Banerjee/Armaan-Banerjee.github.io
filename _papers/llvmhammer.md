## Abstract

- LLM inference relies on optimised GPU kernels generated by just-in-time compilation frameworks such as Triton, which uses an MLIR/LLVM-based pipeline
- A Rowhammer-induced bit flip in the CPU's DRAM can degrade LLM inference performance while preserving output correctness
- The paper introduces LLVMhammer, which induces a bit flip in Triton's compilation pipeline

## Introduction

- Rowhammer attacks traditionally target correctness, and attacks against model weights generally require multiple bit flips
- This paper instead targets vLLM, a GPU-vendor-agnostic framework for LLM inference that uses optimised GPU kernels for operations such as attention and matrix multiplication
- Triton compiles these kernels just in time through a Multi-Level Intermediate Representation (MLIR) and LLVM compilation pipeline
- A bit flip in the Triton binary can alter the generated GPU kernel and degrade performance metrics including time to first token (TTFT), time per output token (TPOT), inter-token latency (ITL), and throughput
- Triton's target-independent optimisation stages create a previously unexplored attack surface
- Finding a suitable function is difficult: the Triton library contains more than 120,000 functions, but only a small number perform target-independent optimisation
- Finding a useful bit-flip location is also difficult: the functions contain around 1.1 million potential locations, but only a few produce a kernel that remains correct and does not crash
- To make this search practical, the authors created Karnage, which identifies useful bit-flip locations

## Background

- When a DRAM row is activated many times within a refresh interval, neighbouring cells can lose charge through capacitive coupling and electromagnetic interference, causing their values to be misread on the next access
- Target Row Refresh (TRR) and Per-Row Activation Counting (PRAC) aim to mitigate Rowhammer by refreshing victim rows after suspicious activation patterns, but Rowhammer remains a threat
- A Rowhammer attack begins with memory profiling: the attacker allocates memory to identify page frames and offsets susceptible to bit flips, then manipulates the victim's memory allocation so sensitive data is placed at a vulnerable location
- Operating-system page-frame allocation is often influenced through memory massaging
- During the hammering phase, the attacker repeatedly accesses aggressor rows to induce bit flips in a neighbouring victim row
- LLVM reduces register pressure and instruction count through optimisation passes, most of which are target-independent; MLIR extends this approach with multiple intermediate representations known as dialects
- Triton is an open-source compiler and Python-based domain-specific language that lets developers write GPU kernels without learning CUDA or another vendor-specific GPU programming model
- Triton first converts a Python kernel into Triton IR, an MLIR dialect, then converts it into the TritonGPU dialect, which represents GPU concepts such as shared memory and synchronisation without being vendor-specific
- The compiler then translates the kernel into LLVM IR, where vendor specialisation targets the NVPTX backend for NVIDIA or AMDGPU for AMD
- Finally, the LLVM backend emits GPU machine code: Parallel Thread Execution (PTX) for NVIDIA or Graphics Core Next (GCN) for AMD
- vLLM is an inference framework that uses PagedAttention to partition the key-value cache and Triton to generate GPU kernels for attention

## LLVMhammer

- LLVMhammer targets code in Triton's target-independent compilation stages
- Karnage systematically reduces the bit-flip search space to a small set of high-confidence locations
- Karnage first identifies candidate functions using namespace filtering and Intel Processor Trace; functions in selected namespaces are guaranteed to be target-independent, while processor traces reveal which functions in `libtriton.so` run when LLM inference kernels are compiled
- This process identifies 254 target-independent functions that run across platforms
- Karnage then identifies CPU instructions in those functions that could produce useful changes when flipped
- Because compilation runs on the CPU, a randomly selected bit flip is unlikely to affect program behaviour; Karnage instead prioritises control-flow instructions that can change the branch taken by the compiler and therefore alter the generated kernel
- Many x86-64 branch instructions differ by a Hamming distance of one, such as `je` (`0x74`) and `jne` (`0x75`), making them practical bit-flip targets
- Evaluating every remaining bit flip with a full inference run would still take too long, so Karnage uses Triton's offline compilation feature and intercepts the kernel launch before GPU execution
- Karnage performs a full inference run only for the bit flips that survive this filtering stage
